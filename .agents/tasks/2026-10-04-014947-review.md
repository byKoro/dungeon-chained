### Canvas-overlay click leak — fixed

The pass-1 defect was that `_onMouseDown` is bound to the container, not the canvas, and the relocated nav buttons are children of that container:

```js
this.container = document.getElementById("canvas-container");
this.container.onmousedown = (e) => { this._onMouseDown(e); };
```

The fix adds a target guard at the top of the handler:

```js
_onMouseDown(e) {
    // Ignora cliques em elementos sobrepostos ao canvas (setas de forma/variação),
    // para que a navegação não dispare mutação na célula do grid por baixo.
    if (e.target !== this.canvas) return;

    if (e.button === 1 || e.shiftKey || e.altKey) { /* pan */ return; }
    if (e.button === 0) { this.isMouseDown = true; this._handleCanvasAction(e); }
}
```

Because the canvas is a direct child of the container and the arrows/variant-bar are siblings layered above it, a mousedown on a button has `e.target` equal to the button element, so the handler returns before setting `isMouseDown` or calling `_handleCanvasAction`. A mousedown on exposed grid area targets `#roomCanvas` directly and proceeds. This resolves the stray hole/enemy/hazard/torch/prop mutation that previously fired on every navigation click.

The guard precedes the pan branch, so it also neutralizes an accidental pan when a modifier key is held while clicking a button. Drag-paint continuation in `_onMouseMove` depends on `this.isMouseDown`, which is now only set on a canvas-targeted mousedown, so painting cannot start from a button either. The acceptance criterion "pointer-events dos botões sobre o canvas não bloqueiam cliques no grid" remains satisfied (the buttons are small and the surrounding grid stays clickable), and the inverse defect is now closed.
